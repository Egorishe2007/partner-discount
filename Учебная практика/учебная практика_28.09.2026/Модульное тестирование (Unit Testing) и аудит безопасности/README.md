# Модульное тестирование (Unit Testing) и аудит безопасности

Задание: перед передачей заказчику доказать, что метод расчета
материалов работает во всех крайних случаях, что интерфейс защищен от
SQL-инъекций, и добавить журнал ошибок.

## 1. Unit-тесты метода расчета

Отдельный модуль `test_material_calculator.py` на `unittest`.
Справочники в тестах — мок-объект `MemoryCatalog` с теми же значениями,
что в `schema.sql`, поэтому база не нужна.

| Тест из задания | Метод | Что проверяется |
| --- | --- | --- |
| Тест 1 (Стандартный) | `test_1_standard_calculation` | ламинат, тип материала 1, 250 шт., 2,5 × 1,2 → ровно **1765** |
| Тест 2 (Округление) | `test_2_fraction_is_rounded_up` | 1764,2625 округляется вверх до 1765, хотя обычное округление дало бы 1764 |
| Тест 3 (Несуществующий тип) | `test_3_unknown_type_gives_minus_one` | тип продукции 99 и тип материала 99 → `-1` |
| Тест 4 (Отрицательные параметры) | `test_4_negative_parameters_give_minus_one` | отрицательный `param_1`, отрицательный `param_2` → `-1` |
| Тест 5 (Нулевое количество) | `test_5_zero_or_negative_quantity_gives_minus_one` | количество 0, −1, −250 → `-1` |

Сверх обязательных — еще 19 тестов:

- **точность:** расчеты для других типов из справочника (526 и 362);
  результат 110 не превращается в 111 из-за погрешности `float`; даже
  2,01 дает 3; результат — именно `int`; параметры в `Decimal` тоже
  принимаются;
- **неверный ввод:** нулевой параметр, текст вместо чисел, дробное
  количество, `True` вместо числа, `NaN` и бесконечность, пропущенные
  значения — везде `-1`, а не исключение; нецелый `id` («1 OR 1=1») даже
  не доходит до справочника;
- **пояснения:** у каждой ошибки свой текст с инструкцией «Пожалуйста,
  …», у верных данных проблемы нет;
- **справочник из базы:** запрос по `id` с параметром, отсутствующий тип
  дает `None`, списки типов превращаются в словари, расчет через
  `DatabaseCatalog`.

## 2. Аудит безопасности: защита от SQL-инъекций

Полей поиска и авторизации в приложении нет, поэтому проверялись все
места, где данные уходят в базу: окно добавления и редактирования
партнера, история продаж, расчет материалов и реестр.

| Где | Запрос | Как передаются данные |
| --- | --- | --- |
| `partner_service.get_partner_ids` | `SELECT id FROM partners ORDER BY id` | данных нет |
| `partner_service.get_partners_with_discounts` | `PARTNERS_LIST_QUERY` | данных нет |
| `partner_service.get_partner_sales` | `PARTNER_SALES_QUERY … WHERE p.id = %s` | `(partner_id,)` |
| `partner_service.insert_partner` — окно добавления | `PARTNER_INSERT … VALUES (%(name)s, …)` | словарь значений формы |
| `partner_service.update_partner` — окно редактирования | `PARTNER_UPDATE … WHERE id = %(id)s` | словарь значений формы и `id` |
| `partner_service.get_sales_history` | `SALES_HISTORY_QUERY … WHERE s.partner_id = %s` | `(partner_id,)` |
| `DatabaseCatalog.product_type_coefficient` | `… FROM product_types WHERE id = %s` | `(product_type_id,)` |
| `DatabaseCatalog.material_defect_percent` | `… FROM material_types WHERE id = %s` | `(material_type_id,)` |
| `get_product_types`, `get_material_types` | списки справочников | данных нет |

**Итог:** все запросы параметризованы — текст запроса постоянный, а
значения psycopg2 передает отдельно и сам экранирует. Конкатенации
строк, f-строк с данными, `%` и `.format()` в запросах нет. Пароль к
базе в коде не хранится, он берется из переменной окружения
`DB_PASSWORD`.

**Что нашел аудит и что исправлено.** В `DatabaseCatalog` оба запроса
выполнялись общим методом `read_value(query, type_id)`, то есть текст
запроса приходил в `execute` переменной. Уязвимости не было — туда
всегда подставлялась константа, — но доказать это проверкой кода нельзя.
Теперь каждый метод вызывает `execute` со своей константой напрямую.

**Проверка закреплена тестами** (`test_sql_safety.py`), чтобы новый код
не мог незаметно нарушить правило:

- по всем модулям приложения (`ast`) ищутся вызовы `execute`, у которых
  текст запроса — не строка в кавычках и не константа модуля;
- константы-запросы, собранные f-строкой, могут подставлять только
  другие константы SQL (так общий список столбцов идет в два запроса
  `partner_service`), но не переменные с данными;
- проверка сначала проверяет саму себя: f-строка, `+`, `%` и
  `.format()` в запросе обязательно ловятся, параметризованный вызов —
  нет;
- попытка инъекции: название партнера `Партнер'); DROP TABLE partners;
  --` уходит в `INSERT` параметром, а текст запроса не меняется; то же с
  `id` вида `1 OR 1=1` в истории продаж.

## 3. Журнал ошибок `app.log`

Модуль `app_log.py` пишет журнал в файл `app.log` рядом с программой:
дата, время, уровень и понятный текст. `python app.py` включает журнал
при запуске.

Запись появляется в каждом блоке `try … except`:

| Событие | Уровень |
| --- | --- |
| реестр, карточка, история или справочники расчета не загрузились из базы | `ERROR` |
| карточка партнера не сохранена, база недоступна | `ERROR` |
| карточка не прошла проверку (например, рейтинг «пять») | `WARNING` |
| расчет материалов вернул `-1` — с входными данными и причиной | `WARNING` |
| расчет не выполнен, база недоступна | `ERROR` |
| не загрузились иконка или логотип | `WARNING` |
| непредвиденная ошибка в любом окне — с полной трассировкой | `ERROR` |

Последняя строка — страховка от критических ошибок: главное окно
переопределяет `report_callback_exception`, куда Tkinter передает любое
необработанное исключение из кнопок и полей. Ошибка попадает в журнал
вместе с трассировкой, менеджер видит окно «CRM: Ошибка», а программа
продолжает работать.

## Файлы

| Файл | Назначение |
| --- | --- |
| `test_material_calculator.py` | unit-тесты метода расчета материалов |
